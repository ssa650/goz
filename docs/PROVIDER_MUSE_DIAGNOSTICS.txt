Provider changes
----------------
Fal errors now carry an allowlisted providerError object:
  provider, httpStatus, requestId, category, detail, stage,
  retryability, automaticRetry.
Detail is sanitized before truncation to 400 characters. Identifiers are bounded
and validated. Only named diagnostic body leaves are selected; arbitrary bodies,
validation inputs and raw headers are excluded. HTML and oversized error bodies
are omitted. Explicit credentials, loaded secrets, bearer/basic/key strings,
URLs, JWT-like strings and long opaque data are removed. A safe x-request-id
header is used only as an identifier fallback; headers are never copied.

Status/result errors preserve the confirmed request ID, actual available HTTP
status, stage and provider category. An HTTP 200 response containing a provider
error retains HTTP 200 in the diagnostic while the application sends an error
response. Malformed JSON and transport errors receive precise categories;
transport exception URLs are omitted. Submission errors remain one-shot and
ambiguous submissions remain blocked across restart.

retryability describes scope: same_request_read, manual_review or none.
automaticRetry=false means the adapter has not retried the failed operation;
the existing engine may reconnect eligible status reads to the SAME saved request.
It never resubmits a generation automatically. Explicit account-lock reports
require manual review even if their HTTP status would otherwise permit a read
reconnect. Cancellation behavior is unchanged; a failed cancel retains safe
context alongside the existing unconfirmed-cancel warning.

Failure metadata persists in job history and private bounded journal
data/diagnostics/provider-errors.jsonl (64 KiB plus one rotated file, mode 0600).
Adaptive public state and provider_failed events retain the same safe object.
Existing UI error text includes stage, HTTP status when known, request ID,
provider detail, and a request/account-review action without asserting a balance
cause or encouraging an automatic paid retry. The FalError API handler exposes
the same safe metadata. Journal write failure does not initiate retries.

Muse diagnostic changes
-----------------------
Explicit producer output now adds a bounded classified observation:
discovery_empty, stream_disconnected, connection_failed, ble_connected, or
stream_started. Both complete and final partial pipe lines are handled.
Classification does not infer a Bluetooth root cause. Loss records include
reader interruption, last sample, producer exit/observation, outlet/acquisition
state, ownership and attempt. Recovery backoff includes nextRetryAt;
fresh sample recovery records recovery_restored.

museConnection adds a bounded message, retryRemaining, recoveryExhausted,
nextRetryAt/retryInSeconds, lastLoss, lastProducerObservation and explicit
bluetoothCause=unknown. The message distinguishes loss, a pending retry and
exhaustion, and gives the existing Connect action for a new explicit intent.
Frontend integration of museState.message is reserved to the parent/UI owner.

Nested diagnostics are sanitized; raw numerical arrays are omitted, device UUIDs
and MAC addresses are redacted, and non-finite numbers become unknown. Rows,
in-memory history, journal rotation and the durable latest-event summary are
bounded even with pathological nested input. Lifecycle scalars survive detail
compaction. Existing Connect intent, finite retry budget, external ownership,
single-reader/producer guards, cooperative stopping and baseline invalidations
are preserved.
